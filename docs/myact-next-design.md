# 次期 MyACT の設計(検討)

`Type: docs`(設計の検討。実装はまだしない)。調べた日: 2026-10-27。

React で大きく作り直すか、myqth の新版と同じ「素の TypeScript + Vite」でやるかを、現状の測定と、旧版・React 版のコードを読んだ事実から比べる。
利用者の決定は、「11. 決定事項」に記録した。

事実には、確かめた方法を添えた。「調査の報告」と書いたものは、コードを読んだ調査の結果で、自分では実行して確かめていない。

## 0. 要約

1. **React 版が止まった原因は、フレームワークではなく、UI の質の基準がなかったこと**。React 版は Claude Code で作り(2025-12-28・29 の 2 日で一気に)、UI の質を上げるのが難しくて中断した(利用者の話)。コードにも、その形跡がある。見た目の基準(旧版の Bootstrap の見た目)を持たず、暗い配色を自作し、ポップアップの仕様(何をどの条件で出すか)も決めないまま、部品だけが先に作られた(6 章)。
2. **推奨: 素の TypeScript(+ Vite)を土台にし、見た目は旧版の CSS をそのまま使う**。myqth の新版で、軽さ(リクエスト 34 → 9、転送量 約 610KB → 約 107KB)と、旧版と同じ見た目の両方が成り立つことを確認済み。React は、地図の部分(Leaflet が自分で DOM を持つ)と相性が悪く、旧版の見た目を保つ助けにもならない。
3. **UI の質は、実装の前に基準を作って守る**: ①画面の仕様(特にポップアップの中身。6 章)を表にする ②旧版を「正解」にして、ポップアップの文言と画面のスクリーンショットを、機械で比べる(golden master) ③新しく設計する面(スポットと地図の一体化。7 章)だけ、静的なモックで合意してから実装する。
4. **フレームワークと関係なく、先に直せる軽量化が 2 つある**: ①`mackerel.io` の iframe が、モーダルを開かなくても起動のたびに 約 3.5MB と広告・計測のスクリプトを読んでいる(遅延読み込みにする) ②公園区域の TopoJSON(初回 約 5.5MB 転送)の簡略化・分割(8 章)。
5. **段階的に、`myact2` で公開しながら**移す。旧版は止めず、切り替えと戻し方は myqth と同じ(9 章)。
6. **POTA ログとパドルエミュレータ(ActPaddle)は必須。最初のリリースに入れる**(利用者の指示。POTA ログは、一番使われている機能)。POTA ログは、地図の表示(マーカーの色・ポップアップの QSO 数)を決める入力でもあるので、マーカーと同じ段階で作る(6.6・6.7・9 章)。
7. **決定済み(11 章)**: 素の TS で進める・廃止する機能・スポットは案 A・Cookie は読み書き・`apps/myact-next`。

## 1. 目的と制約

- **軽くて、すぐ出る**(山の上の弱い回線でも起動する)。
- **見た目は旧版のまま**(Bootstrap 4.5 + MDB のナビバー・ボタン・モーダル。利用者が慣れている)。
- **旧版を止めずに**、機能ごとに移す。いつでも旧版に戻せる。
- 地図まわり(ポップアップ・マーカー・公園区域・アクティベーションゾーン)の**表示内容を落とさない**。
- UI は Claude Code で実装する。**質を上げやすい進め方**にする(0 章の 3、9 章)。

## 3. React 版の現状(調査の報告を、確かめた範囲で)

確かめたこと(自分で `grep`・`wc` を実行):
- `PotaLogManager`(289 行)と `KeyerPanel`(288 行)は、どこからも import されていない(画面に出ない)。
- 地図の空白をクリックしたとき `setActivePopup` を呼ぶが、`activePopup` を読んで描く所がない(`stores/mapStore.ts` に定義があるだけ)。**地図の空白をクリックしても、ポップアップが出ない**。
- 旧版の設定のうち、React 版の地図が使っていないもの(設定画面と型・辞書を除いた使用箇所が 0): `pota_ref`・`jaff_ref`・`link_googlemap`・`display_mapcode`・`enable_emulation`・`pilgrim`・`pota_log`。
- `?lat=&lon=&z=` の URL 指定は未実装(`URLSearchParams` は API クライアントにしかない)。
- テストは 4 件(XSS の確認だけ)。マーカー・スポット・検索・設定・ログ・キーヤーには、振る舞いを守るテストがない。
- 見た目: 自前の暗い配色(`#1a1a2e`)で、Bootstrap・MDB は使っていない(旧版と別物)。
- 最終の機能追加は 2025-12-29。その後は 2026-10-21 の整備(lint・docs)と XSS の修正だけ。

調査の報告(未確認): 地図の中心とズームの二方向の同期を、`isExternalUpdate` という ref のフラグで避けている(壊れやすい)。マーカーの取得・ポップアップの詳細の取得・地図の同期が、3 通りの書き方に割れている。

**止まった理由**: 利用者の話では、Claude Code で実装し、UI の質を上げるのが難しくて中断した。コードの形跡は、これと合う。見た目の基準が旧版の CSS にない(自作の暗い配色)。ポップアップの仕様が決まっていない(空白クリックは未接続、設定の多くが未反映)。画面の設計(スポットと地図の一体化)は案のまま(`FEATURES.md` の「改善候補」)。**AI が実装するとき、「正しい見た目」と「正しい中身」の基準がないと、質が上がらない**。React でも TS でも同じ。

## 4. 選択肢

| | A. React を続ける/作り直す | B. 素の TS(推奨) | C. 軽い UI ライブラリ(Preact など)を、フォームの部分だけに |
|---|---|---|---|
| 地図との相性 | react-leaflet が Leaflet と React の二重の仕組みになる(同期のフラグが要る。ポップアップは Leaflet が DOM を持つので、ポータルで描く) | Leaflet をそのまま使う(myqth で実績) | B と同じ。地図は素の TS |
| 見た目を旧版のまま | 旧版の CSS を持ち込めるが、JSX で組み直すので、手間と差が出る | **旧版の HTML・CSS をほぼそのまま使える** | 同じ |
| 軽さ | React + react-dom + react-leaflet で 初回 JS gzip 157KB(今)。Recharts +104KB | 素の TS + Leaflet で 47KB(myqth の実績)。チャートは Chart.js(旧版と同じ)を遅延 | + 約 4KB(Preact) |
| 設定(約 35 項目)・POTA ログ・一覧などフォーム中心の画面 | **得意** | 手で DOM を書く(量が多い。ただし、1 つの小さな部品にまとめれば足りる) | **得意な部分だけ使う** |
| テスト | 部品ごとに書ける | 「データ → 表示」を純粋な関数にして、vitest で守りやすい | 同じ |
| AI が実装するときの質 | 基準がないと質が上がらない(実際に止まった) | 旧版の HTML・CSS・文言を基準にできる | 同じ |
| 移行の段階 | 地図と状態の同期を作り直すので、最初の公開までが長い | 地図 → ポップアップ → マーカー…の順に、myqth の延長で進められる | 同じ |

**推奨: B を基本にする。設定・POTA ログ・ActPaddle はフォーム中心で、必須の機能なので、C(Preact など)が要るかは、段階 0 の試作(POTA ログのダイアログを素の TS で書いて量を見る)で判断する**。最初から入れない。

React 版を捨てる損失は小さい。再利用できるのは、型定義(`types/api.ts`)、逆ジオコーダー(`@sotalive/geo` に既にある)、アクティベーションゾーン(`L.GridLayer` のアルゴリズムは Leaflet だけで書ける)、公園区域の変換、翻訳の辞書。

## 5. アーキテクチャ(B の場合)

myqth と同じ作りを広げる。`apps/myact`(React 版)は凍結し、新しいアプリを `apps/myact-next` に作る(決定済み)。

```
packages/
  geo/               逆ジオコーダー・グリッドロケーター・escapeHTML(あり)
  sotaapp-api/       型付きの API クライアント(/search・/sota・/pota・/activation・/propagation)。fetch を差し替えられる
  myact-core/        地図に載せるデータの取得と整形(フレームワークなし。vitest で守る)
                       prefs(型つき・旧版の Cookie と互換)、markers(世代管理・中断)、popup-model(6 章)、spots
apps/
  myact-next/        Vite + 素の TS。Leaflet、旧版の Bootstrap 4.5 の CSS、画面(ナビバー・ポップアップ・パネル・設定)
```

- **状態**: 小さな型つきのストア(購読できるオブジェクト)。旧版のグローバル変数と、DOM との双方向の同期(`clickPrefs`)をやめる。
- **prefs**: 旧版の Cookie 名・値(約 35 項目。`expires` 1800 日)をそのまま読み、書く。**切り替えても、利用者の設定を引き継ぐ**。
- **データの取得**: 地図の移動ごとに、前の取得を中断して(`AbortController`)、最新の結果だけを使う(旧版は、古い結果が新しい結果の上に重なる)。同じ範囲・条件の結果はキャッシュする。
- **ポップアップ**: HTML の文字列を連結しない(旧版は一部が未エスケープ)。「データ(モデル)」を作る関数と、それを DOM にする関数に分ける(6 章)。
- **見た目**: myqth と同じく、Bootstrap 4.5 の CSS と、旧版が MDB・Semantic UI から受けていた分だけを `style.css` に写す。

### 6.5 新版の方針(ポップアップ)

1. **仕様を表にする(上の 6.1〜6.4)ことを、最初の作業にする**。表の行が、実装とテストの単位になる。
2. **旧版を「正解」にして、機械で比べる(golden master)**: 旧版を Playwright で開き、API を固定の応答に差し替えて、表の操作ごとにポップアップの表示テキストを記録する(山・公園・空白・圏外・GPS・設定の組み合わせ)。新版は同じ入力で、同じテキストを出すことをテストする。意図して変える所だけ、差分を明示する。myqth で、旧版と同じ固定の応答・同じ文言のテストを作って、効果を確かめた方法の拡張。
3. **データ → 表示の 2 段に分ける**: 「どの API を呼んで、どのブロックを出すか」を決める関数(`popup-model`。vitest で全組み合わせを守る)と、それを DOM にする関数(外から来る値は `textContent` で入れる)。
4. 設定(`pota_ref` など)は、**ポップアップとマーカーが実際に読む**ようにする(React 版は 7 項目が未反映)。

### 6.6 POTA ログ(最優先。一番使われている機能)

`potaLog()`(`myact.js:188-338`)・`getLogID()`・設定画面の HTML(`index.html:380-426`)・`displayPopup`/`redrawMarkers` の `log_id` を読んだ(自分で読んだ)。

ログは**サーバー側(sotaapp2)に UUID で保存**され、ログインはない。UUID は Cookie(`pota_activator_uuid`・`pota_hunter_uuid`)にある。**新版でも同じ Cookie 名で引き継がないと、利用者のログが見えなくなる**。

| 操作 | 旧版の挙動 | API |
|---|---|---|
| 確認(設定を開いたとき) | UUID があれば取得し、「最終更新(Activator)」「(Hunter)」と表示。無効なら UUID を捨てて `----` | `GET /pota/log/{uuid}` → `logId`・`lastUpdate` |
| アップロード | POTA.app の CSV を選んで Upload。`logKind`(activator/hunter)に応じて UUID を保存し、そのログの表示に切り替える。失敗は「不正なログファイルの形式です…」の alert | `POST /pota/log/{activator}/{hunter}`(FormData `uploadfile`)→ `logKind`・`logId` |
| 削除 | Activator・Hunter それぞれの DEL。削除したら、もう一方の表示に切り替える | `DELETE /pota/log/{logId}` |
| 共有(EXPORT) | 共有キーを表示 | `GET /pota/log-share/{activator}/{hunter}` → `share_id` |
| 共有(IMPORT) | キーを入れて、両方の UUID を取り込む。なければ「キーコードが見つかりません」 | `GET /pota/log-share/{key}` → `activator_logid`・`hunter_logid` |
| 表示の切り替え | 「POTA ログを表示」(`show_potalog`)と、Activator か Hunter か(`show_potaactlog`)。`getLogID()` が、どちらの UUID を地図に使うかを決める | (なし) |
| **地図への反映** | 地図・ポップアップの取得に `log_id` を付ける。**公園マーカーの色**(未活動 `green-light`・活動済 `red`・複数 `orange`・試行のみ `yellow`)と、**ポップアップの Activations/Attempts・QSOs** が変わる | `/search`・`/pota/parks/search`・`/sota/summits/search` の `log_id` |
| 統計 | 「POTA ログ表示」の横のボタンで統計のモーダル。Chart.js の棒グラフ | `GET /pota/log-stat` |

React 版は、`PotaLogManager`(289 行。アップロード・共有・削除の API 呼び出しがある)が**画面に載っていない**。マーカーの色とポップアップの数は、`logId`(hunter 優先)が入れば動く。再利用の候補。

**受け入れ**: 固定の応答で、アップロード → 表示の切り替え → マーカーの色・ポップアップの数、までを golden master にする。削除・共有・失敗の alert の文言。**Cookie の互換**(旧版で保存した UUID が、新版で読める)。

### 6.7 パドルエミュレータ(ActPaddle)

`keyerButton`・`clickPemuAct`・`open_serial`・`pemuPressed`(`myact.js:349-495`)と、モーダル(`index.html:451-`)を読んだ(自分で読んだ)。

| 項目 | 旧版の挙動 |
|---|---|
| 入口 | 設定 `enable_emulation` がオンのとき、ポップアップの下にクリップボードのボタン(B6)。押すと ActPaddle のモーダル |
| 引き継ぐ値 | ポップアップの場所の参照: SOTA・POTA・JAFF・エリアコード・JCC/JCG・名前 |
| 入力 | CALL・エリアコード(CALL に付けるか: `include_areacode`)・JCC/JCG・SOTA・POTA・JAFF・メッセージ 4 本(それぞれ SEND)・WPM・送り先のホスト・パドル/ストレート(`to_paddle`)・反転(`paddle_reverse`)・WiFi か USB か(`enable_wifi`) |
| 送る内容 | メッセージを大文字にし、`$CALL`・`$SOTA`・`$POTA`・`$JAFF`・`$JCC`・`$JCG` を置き換え(参照のハイフンは除く)。`{wpm, to_paddle または to_straight, reverse}` の JSON + CR。**クリップボードにもコピー** |
| 送り方 | WiFi: `https://<host>/play` に POST。USB: Web Serial(115200bps。USB ID 4 種: ESP32-S3・FTDI・CH340・CP210x)に書き、1 回読む |
| 保存 | `pemu_*` の全項目を Cookie に保存 |
| エラー | 接続エラー・シリアル非対応を alert |

**旧版の不具合**(新版で直す。挙動が変わるので、あなたの確認が要る): `$CALL` などを**最初の 1 つしか置き換えない**(`String.replace`)。`Content-Type` が `applicatoin/json`(誤字)。`if (! "serial" in navigator)` の優先順位の誤りで、非対応のブラウザーに alert が出ない。

**制約**: Web Serial は、Chromium 系の PC・Android だけ(iPhone・Safari は使えない)。WiFi は `https://` 固定(機器側が https)。

**テスト**: メッセージの組み立て(置き換え・JSON)は純粋な関数にして、vitest で全組み合わせを守る。WiFi は POST の宛先を差し替えて、中身を確かめる。Web Serial は `navigator.serial` を差し替える。**実機(ESP32 など)は、こちらでは確かめられない**ので、利用者に確認してもらう。React 版の `KeyerPanel`(288 行)も、画面に載っていない(Web Serial の一部と WPM の入力がある)。

## 7. 画面の設計(止まっていた所)

面を 3 つに分ける。同時に開く面は、**地図 + 1 つだけ**にする(旧版は、設定のモーダルの中から統計のモーダルを開いて、重なる)。

| 面 | 内容 | PC | モバイル |
|---|---|---|---|
| 地図のポップアップ | クリックした所の情報(6 章)。軽い、すぐ閉じる | Leaflet のポップアップ | 同じ(ポップアップ。長いときは中でスクロール) |
| 詳細 | 選んだ山・公園の詳細(今ポップアップに全部入れている情報の、長い版)や、設定 | 右の側パネル | 下からのシート |
| スポット | 一覧とチャート(今のモーダル) | 右の側パネル(常時開ける) | 下からのシート |

「スポットを地図と一体にする」の定義(案):
- スポットを**選ぶ**(クリック・タップ)と、地図がその参照へ移動し、マーカーを強調し、ポップアップを開く。
- **ホバー(ツールチップ)では地図を動かさない**。旧版は、ツールチップを出すだけで地図が動く副作用がある(`label_callback` の中の `locate_ref`)。
- 閉じ方: パネル右上の × と Esc。背景のクリックで閉じるのは、モーダルのときだけ。

**案 A(推奨)**: 上の表のとおり、側パネル/シートに統一する。**案 B**: 当面は、旧版のモーダルと同じ見た目・操作で移し、統一は、全部が移ってから別の作業にする。

**UI の質を保つ進め方**: 面の設計は、実装の前に、**静的な HTML のモック**(旧版の Bootstrap の見た目で、ダミーのデータ。PC・iPhone・iPad の 3 サイズ)を作り、あなたが見て合意してから、実装する。AI に「いい感じの UI」を作らせない。配色・余白・フォントは、旧版の CSS(Bootstrap 4.5 + MDB の分)から決まるので、AI が発明しない。
